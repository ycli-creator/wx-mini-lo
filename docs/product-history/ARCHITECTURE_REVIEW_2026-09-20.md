# 架构检查：2026-09-20

## 结论

当前分层可以支持本次首期改动，不需要推倒重来：

```text
页面 -> love-points service -> runAction -> api action -> CloudBase
```

任务、积分、通知、记录和文档已经有独立入口，适合继续按领域扩展。

## 已发现的架构问题

1. 任务模型把 `shared` 积分和情侣空间强绑定，首期新任务需要改为个人积分。
2. `notifications` 目前是 App 内通知，没有接微信订阅消息发送器。
3. `coupleId` 是当前共享空间主键，短期可作为 `workspaceId` 的兼容实现，但不能现在一次性重命名所有集合。
4. 社区帖子和日常记录的数据模型已有媒体字段，但社区服务主动拒绝图片/视频，快速发布需要复用媒体上传能力并补审核边界。
5. 文档目前只有文档组和纯文本正文，目录、导入和图片资源需要独立的后续数据模型。

## 本次代码改动范围

- 新建任务增加完成人和是否需要确认的产品字段。
- 新任务默认使用个人积分；旧 `shared` 数据保留兼容读取。
- 不需要确认的任务提交后直接完成并结算个人积分。
- 保留 App 内通知作为基础能力。
- 记录工作区抽象、迁移和媒体审核要求，暂不执行线上部署。

## 后续部署前必须完成

- 双账号验证双方完成任务各自入账。
- 双账号验证审批通知和重复点击幂等。
- 配置微信订阅消息模板、用户授权和云函数发送权限。
- 对历史共同积分任务制定迁移或只读兼容策略。
- 图片上传接入媒体安全检查后再开放生产入口。
