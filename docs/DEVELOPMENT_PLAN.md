## 1. 项目结论

Love Points 是一个以一对一情侣空间为核心的微信原生小程序。产品通过“任务—审批—积分—奖励—共同记录”形成互动闭环，并在 V2 增加个人资料、公开情侣社区和生活日历。

V1 不做公开社区的限制已经由后续需求更新。V2 仍不做 H5、独立 App、真实商品、支付、物流、现金账单或复杂协同编辑。

## 1.1 V2 新增范围

- 首次进入先填写用户名、头像、性别、地区与爱好；“我的”Tab 改为独立个人页，设置成为二级页面。
- 奖励商店从第三个 Tab 移入任务页，通过“任务 / 奖励商店”分段切换。
- 第三个 Tab 改为公开情侣社区，使用双列 Feed；支持纯文字、照片和视频。
- 社区帖子先保存为待确认状态，只有发布人的伴侣同意后才公开；公开卡片强调情侣组合，个人性别、地区和爱好不随帖子公开。
- 增加生活日历，可按日期记录情绪、事件和经期。所有记录默认仅自己可见，可主动选择与伴侣共享。
- 新增 `community_posts` 和 `daily_records` 集合；个人资料继续保存在 `users` 集合。
- 社区文字与公开昵称通过微信内容安全接口检查；图片、视频还需在正式提审前完成媒体审核策略和隐私协议配置。

历史产品文档中存在“多人关系空间、H5/App、多种记录工具、真实账单”等较大范围。当前开发以用户后来确认的新规则为准：仅微信小程序、仅两人一对一绑定、保留个人与共同积分、奖励可退款、文档先做简单编辑、解绑需要双方同意并清空情侣空间数据。

## 2. 已确认的产品规则

### 2.1 用户与绑定

- 一个情侣空间固定只有两名成员。
- 一方创建邀请，通过微信小程序卡片分享给另一方。
- 邀请同时生成 6 位短码，默认 30 分钟有效、一次性使用。
- 对方打开分享卡片并输入短码后，邀请方再确认一次，绑定才正式成立。
- 绑定成功后双方可以共同管理任务、积分、奖励和文档。

### 2.2 解绑

- 任意一方可以发起解绑。
- 发起后进入等待状态，情侣空间仍可正常使用，数据保持不变。
- 只有双方都明确同意后才解除绑定。
- 对方拒绝、发起方取消或请求超时，均保持原绑定关系。
- 双方确认解绑后，立即清空该情侣空间内的任务、任务提交、个人与共同积分、积分流水、奖励、兑换记录、文档和操作记录。
- 微信用户身份保留，之后可以重新发起新的绑定。

### 2.3 任务与积分

- 保留个人积分和共同积分两套账户。
- 个人任务：本人提交完成，由对方审批；通过后发放本人的个人积分。
- 共同任务：一方提交完成，由另一方确认；通过后发放共同积分。
- 任务可被驳回并重新提交。
- 积分余额不允许由前端直接改写；所有获得、消费、退款和冲正都必须产生不可修改的积分流水。
- 任务审批、积分变动和业务状态更新必须在服务端事务中完成，并使用幂等键防止重复点击造成重复加分。

### 2.4 奖励与退款

- 双方都可以创建自定义奖励。
- 奖励字段包括：名称、说明、积分类型、消耗积分、有效期、是否需要对方同意、文字形式的使用条件。
- 每个奖励只能指定使用个人积分或共同积分，V1 不做混合支付。
- 无需审批的奖励可直接兑换；需要审批时由对方确认后完成兑换。
- 兑换成功后生成负向积分流水。
- 已兑换奖励可以申请退款；对方同意后返还积分并生成退款流水。
- V1 不做真实商品、库存、支付、物流或现金退款。

### 2.5 共享文档

- 双方可以创建文档组，例如“日记、攻略、共同计划”。
- 文档支持标题、纯文本正文、创建人、最后编辑人和更新时间。
- V1 不做逐字实时协同、富文本、版本分支或复杂附件。
- 首版采用单人编辑锁：一方编辑时另一方只读；保存后再同步最新内容。

## 4. V1 核心流程

### 4.1 绑定流程

`初次进入 → 创建邀请 → 微信分享 → 对方输入短码 → 邀请方确认 → 首页`

### 4.2 任务与积分流程

`首页任务卡 → 提交任务 → 对方审批 → 写入积分流水 → 积分中心`

### 4.3 奖励与退款流程

`积分中心/首页 → 奖励商店 → 奖励详情 → 兑换 → 已兑换 → 申请退款 → 对方处理 → 返还积分`

### 4.4 文档流程

`首页 → 文档库 → 选择文档组/新建文档 → 编辑 → 保存 → 双方查看`

### 4.5 解绑流程

`设置 → 发起解绑 → 等待对方 → 对方同意/拒绝 → 双方同意后清空情侣空间`

## 5. 技术方案

### 5.1 客户端

- 微信原生小程序。
- TypeScript + WXML + WXSS + JSON。
- 不引入 uni-app、Taro、React、Vue 或 Tailwind，减少编译层和跨端适配成本。
- UI 基础组件使用 `tdesign-miniprogram`，业务卡片和设计稿特有组件在项目内封装。
- 图标优先使用 `tdesign-icons` 中与 Figma 一致的图形。

选择微信原生小程序的原因：当前明确不做其他端，原生方案最贴近微信分享、登录、订阅消息和云开发能力，也更容易直接在微信开发者工具中调试。

### 5.2 后端

- 腾讯云 CloudBase 云开发。
- V1 使用 CloudBase 文档数据库、云函数和云存储，不额外搭建服务器或 MySQL。
- 所有身份校验、绑定、任务审批、积分变动、兑换、退款和解绑都在云函数中执行。
- 初期采用一个 `api` 云函数作为路由入口，内部按领域拆分模块；规模增加后再拆成多个云函数。

对于只有两名用户的小项目，文档数据库足以支撑 V1，部署和维护明显轻于独立 MySQL。数据模型会保留清晰的 `coupleId` 和不可变流水，后续仍可迁移到关系数据库。

### 5.3 安全原则

- 客户端永远不直接修改积分余额、审批结果或兑换状态。
- 每个业务请求都从云函数上下文读取当前用户 OpenID，不接受客户端伪造身份。
- 所有数据按 `coupleId` 隔离，并校验当前用户是否为该空间成员。
- AppSecret、CloudBase 密钥和其他凭据不得写入仓库或发送到聊天中。
- 高风险操作写入操作日志；积分流水不可覆盖，只能追加反向流水冲正。

## 8. 数据模型

所有业务集合都包含 `_id`、`coupleId`、`createdAt`、`updatedAt`，删除默认使用逻辑删除；只有双方确认解绑时执行情侣空间级清理。

### 8.1 集合

- `users`：OpenID、昵称、头像、当前 coupleId。
- `couples`：成员 OpenID、绑定状态、绑定时间、解绑状态。
- `invites`：短码哈希、创建者、申请者、有效期、状态、使用次数。
- `tasks`：任务类型、执行人、审批人、积分类型、积分值、截止时间、状态。
- `task_cycles`：每日、每周与长期计划的周期实例、周期边界、结算状态和当前提交。
- `task_submissions`：完成说明、凭证、提交人、审批结果、驳回原因、周期编号和幂等键。
- `point_accounts`：成员个人余额、情侣共同余额；只由云函数事务更新。
- `point_ledgers`：账户、方向、金额、来源类型、来源 ID、操作人、冲正关系、幂等键。
- `rewards`：名称、说明、积分类型、价格、有效期、审批要求、使用条件、状态。
- `redemptions`：兑换人、奖励快照、扣分流水、审批、使用状态、退款状态、退款流水。
- `document_groups`：名称、排序、创建人。
- `documents`：文档组、标题、正文、编辑锁、最后编辑人。
- `notifications`：绑定、审批、兑换、退款和解绑通知。
- `operation_logs`：高风险操作、操作人、对象、结果和时间。

### 8.2 重要约束

- 一个用户同时最多属于一个有效情侣空间。
- 一个有效情侣空间必须且只能有两名成员。
- 同一个业务动作的幂等键只能成功一次。
- 积分流水一经创建不可修改或删除。
- 账户余额变化值必须等于对应流水变化值。
- 退款只能针对有效兑换记录，且最多成功一次。
- 解绑清理只能在双方确认状态下执行。

## 9. 云函数接口

初期统一调用：`wx.cloud.callFunction({ name: 'api', data: { action, payload } })`。

| 领域 | Action | 说明 |
|---|---|---|
| 身份 | `auth.login` | 登录、创建或更新用户 |
| 邀请 | `invite.create` | 创建短码与分享参数 |
| 邀请 | `invite.apply` | 校验短码并提交绑定申请 |
| 邀请 | `invite.review` | 邀请方同意或拒绝 |
| 首页 | `home.summary` | 首页聚合摘要 |
| 任务 | `task.list/create/detail` | 任务列表、创建和详情 |
| 任务 | `task.submit` | 提交完成记录 |
| 任务 | `task.review` | 审批并事务写入积分 |
| 积分 | `points.summary` | 个人与共同余额 |
| 积分 | `points.ledger` | 流水列表与筛选 |
| 奖励 | `reward.list/create/detail` | 奖励列表、创建和详情 |
| 奖励 | `reward.redeem` | 校验余额并兑换 |
| 奖励 | `reward.refund.request` | 发起退款申请 |
| 奖励 | `reward.refund.review` | 审批并返还积分 |
| 文档 | `documents.groups/list/save` | 文档组、列表与保存 |
| 文档 | `documents.lock/unlock` | 简单编辑锁 |
| 解绑 | `unbind.request/cancel/review` | 发起、取消、同意或拒绝 |

## 11. 实施顺序

### 阶段 0：本地 Web 交互原型（当前）

- 使用 React + TypeScript + Vite 建立独立的 `web-prototype` 工程。
- 按 Figma 的 16 个画板实现页面、视觉与核心点击流程。
- 在 Figma 流程页之外补充完整 App 外壳：`首页 / 任务 / 奖励 / 文档 / 我的`五项底部 Tab；积分与各类详情页作为二级页面。
- 使用浏览器本地存储模拟任务、积分、奖励、文档和解绑状态。
- 不接入微信登录、分享、CloudBase、云函数或真实双人同步。

退出条件：原型可通过本地地址直接运行，16 个页面均可访问，五条核心流程可独立演示，并通过类型检查、生产构建和浏览器检查。

### 阶段 1：工程与视觉骨架

- 初始化微信原生 TypeScript 小程序。
- 接入 TDesign 和图标。
- 建立 Figma Token、基础组件和 16 个页面路由。
- 用 Mock 数据完成全部页面跳转。

退出条件：16 个页面均可打开，核心按钮可点击，视觉与 Figma 首轮一致。

### 阶段 2：绑定与首页

- CloudBase 初始化、登录、用户与情侣空间。
- 邀请短码、微信分享、绑定申请和确认。
- 首页摘要与未绑定/已绑定状态。

退出条件：两台设备可完成邀请与一对一绑定。

### 阶段 3：任务、审批与积分

- 任务创建、提交、审批和驳回。
- 个人/共同积分账户与不可变流水。
- 幂等与事务验证。

退出条件：重复点击不会重复加分，流水和余额一致。

### 阶段 4：奖励、退款与文档

- 奖励创建、兑换和退款。

退出条件：奖励兑换/退款和文档编辑可以由两名成员完整走通。

### 阶段 5：解绑与完整验收

- 双方确认解绑与数据清理。
- 空状态、加载、错误、权限和危险确认状态。
- iOS 与 Android 微信真机检查。

退出条件：五条主流程全部通过，解绑前后数据状态正确。

## 12. V1 验收清单

- [ ] 新用户能创建邀请，另一名用户能通过分享卡片和短码申请绑定。
- [ ] 邀请方确认后，双方进入同一个情侣空间。
- [ ] 一名用户能提交任务，另一名用户能审批或驳回。
- [ ] 审批通过只产生一次正确的个人或共同积分流水。
- [ ] 余额、流水、任务和兑换状态在重试后保持一致。
- [ ] 双方都能创建自定义奖励，并选择个人或共同积分。
- [ ] 积分不足时无法兑换；退款通过后只返还一次积分。
- [ ] 双方能创建文档组与简单文档，编辑锁能避免同时覆盖。
- [ ] 非情侣空间成员无法读取任何情侣数据。
- [ ] 一方发起解绑不会立即清空数据；双方同意后才清空。
- [ ] 所有页面有基础空状态、加载状态、失败重试和危险确认。
- [ ] 16 个页面在常见微信屏幕宽度下无横向溢出和文字裁切。
